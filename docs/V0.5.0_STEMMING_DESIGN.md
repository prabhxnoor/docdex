## 1. Goal

Make morphological variants of a word count as the same word during retrieval,
so a search or `context` task for **`governing`** also finds **`governed`** and
**`governs`**, `close` finds `closed`, `deal` finds `deals`. This closes part of
the M1 gap ("match meaning, not just words") and is the roadmap's explicit
**first** M1 step, gated behind the v0.4.0 field-local extraction fix.

Success = higher recall on real tasks **without** making the packet confidently
wrong: exact answers (IDs, amounts, dates) stay literal, and the agent is told
when a match is approximate so it can verify.

## 2. Decisions (from brainstorming, 2026-07-19)

1. **Favor recall (aggressive stemming).** Use a full Porter stemmer, not a
   light plural-only one. We accept that Porter over-merges some distinct words
   (`organization → organ`) in exchange for maximum recall, and recover precision
   at the **agent layer** (below) now and in the **utility reranker** (piece #3)
   later — the standard hybrid-retrieval pattern (recall first, rerank for
   precision).
2. **Add an LLM-side recall guardrail** — the agent must know when a hit is a
   stem-only (approximate) match so it can down-weight or verify it. This is the
   "check on the LLM side" that the recall choice is paired with.
3. **Recall-only scope for this PR.** Stemming applies to search, `context`
   evidence, the match-existence check, and the no-FTS5 fallback scorer. **Form
   field-value extraction stays literal** in this piece and becomes a roadmap
   follow-up folded into the alias/reranker pieces (which rework that code).
4. **The binary-file fix folds into v0.5.0.** It is already staged in
   `CHANGELOG.md [Unreleased]` and ships in the v0.5.0 notes; no separate v0.4.2.

## 3. Architecture — two layers, one source of truth

docdex has one tokenizer (`search.tokenize`) that is used both to build the
search query **and**, inside the packet, to re-check "is this chunk really a
match?" (`context._candidates.keep`, `context.py:106`). So stemming must be
consistent across those, or the index would surface `governed` for a `governing`
query and the packet would then discard it as a non-match.

The design uses two cooperating layers:

- **Recall funnel (fast, in SQLite).** The FTS5 index switches to SQLite's
  built-in **`porter`** tokenizer (`porter unicode61`). FTS5 then stems both the
  stored chunk text and the `MATCH` terms itself, so `governing` matches stored
  `governed` with no query rewriting. This is the recall win on the 95% path.
- **Authoritative check (Python).** A new dependency-free `stemming.stem()` is
  the source of truth for what is *reported* as a match. The packet's `keep()`
  existence filter and the no-FTS5 fallback scorer both stem through it.

**Why two layers instead of one:** FTS5's Porter and our vendored Python Porter
do not need to agree byte-for-byte. FTS5 is only a cheap *recall superset* — it
returns candidate chunks. Our Python stemmer is the authority that decides which
candidates are reported as matches. Worst case of any divergence: FTS returns a
chunk our `keep()` drops (fine), or misses one our stemmer would keep (small
recall loss). The only hard requirement is that **our** stemmer maps `governing`
and `governed` to the same stem — which a correct Porter does. This removes the
fragile "two stemmers must be identical" coupling.

### Where stemming applies — and where it must not

| Use | Operation | Stemmed? |
|-----|-----------|----------|
| FTS5 index + `MATCH` | recall funnel | ✅ (SQLite porter) |
| `keep()` existence check | set membership | ✅ (Python `stems()`) |
| Fallback `score_text` | token-multiset counting | ✅ (Python `stems()`) |
| `--explain` display | show stems | ✅ |
| Value/ID/amount/date extraction (`VALUE_RE`) | literal from raw text | ❌ never |
| `_label_window` / `snippet` positions | substring offsets in raw text | ❌ never |
| Form field-value extraction | literal (deferred) | ❌ this PR |

The rule: stemming touches **set-membership matching and ranking only**. Any code
that computes a **position or count against raw text** (`rfind`, `count`,
snippet windows) stays on literal tokens — a stem is often a prefix (`companies →
compani`) and would land mid-word. Displayed values are always the literal
string, so exact-answer honesty from v0.4.0 is untouched.

## 4. New module: `stemming.py`

A compact, **dependency-free** Porter stemmer (public-domain algorithm), plus
helpers and guardrails:

```python
def stem(token: str) -> str: ...          # Porter stem of a single token
def stems(text: str) -> set[str]: ...      # {stem(t) for t in tokenize(text)}
```

Guardrails (both the Python stemmer and the tests enforce these):

- **Never stem non-word tokens.** A token containing a digit (`gstr3b`,
  `42000000`) or any non-ASCII letter (`échéance`, Devanagari) is returned
  unchanged — Porter is English/ASCII-only, and literal identifiers must be
  preserved (a documented BM25 best practice).
- **Never stem very short tokens** (already handled: `tokenize` drops <2 chars;
  Porter no-ops on ≤2-letter stems).
- **Deterministic** — the same input always yields the same stem. Applied to RAW tokens only: this is single-pass canonical Porter (mirroring SQLite FTS5's `porter`), so it is NOT idempotent (`stem(stem(x))` may differ from `stem(x)` for some words) — never feed it already-stemmed output.

`tokenize()` itself is **unchanged** (still literal, Unicode-aware) because the
position/count code paths depend on it. Stemming is a *layer on top* via
`stems()`, not a change to `tokenize()`.

## 5. The LLM-side recall guardrail

Because recall over-merges, the agent needs to know when evidence is approximate.
Three deterministic, honest signals (extending v0.4.0's found/weak/missing
language to exact/approximate):

1. **Provenance marking per evidence line / answer.** A hit is **exact** when
   every matched query content-term appears *literally* in the chunk; **`~approx`**
   when at least one matched only through its stem. Cheap: literal-substring
   check on the raw chunk text. Approximate lines are tagged in the packet, with
   a one-line legend the first time one appears.
2. **`--explain` shows the stems.** e.g. `governing → govern (also matches:
   governed, governs)`, so the widening is visible and deterministic.
3. **Scaffold guidance.** `AGENTS.md` / `CLAUDE.md` templates gain one line:
   *"Evidence may include approximate word-stem matches (tagged `~approx`);
   confirm the literal term before asserting a fact. IDs, dates, and amounts are
   matched literally."*

Full precision recovery (dropping loose stem matches) is the **utility reranker**
(piece #3) — the industry-standard place for it. This piece ships *awareness*;
#3 ships the *filter*.

## 6. Migration / index rebuild

Changing the FTS5 tokenizer requires recreating the `chunks_fts` virtual table,
which `CREATE ... IF NOT EXISTS` will not do on an existing DB. Plan:

- Bump `index_db.SCHEMA_VERSION` (`"1"` → `"2"`).
- In `build()`, read the stored `meta.schema`; if it differs from
  `SCHEMA_VERSION`, `DROP TABLE IF EXISTS chunks_fts`, clear `files`/`chunks`,
  and force a full reindex so `_init_schema` recreates `chunks_fts` with the
  `porter` tokenizer and every chunk is re-added.
- Net effect for a user: the first `docdex sync` after upgrading rebuilds the
  lexical index once (from the `.txt` caches, the source of truth). No user
  action, no data migration — rebuildable state rebuilding itself, exactly as the
  "lean by default" design intends.

## 7. Testing plan (TDD, repro-first — one test per behavior)

New `tests/test_stemming.py`:

- **Unit (`stemming.py`):** `governing`/`governed`/`governs` and `deal`/`deals`
  share a stem; `stem` is deterministic (single-pass Porter, not idempotent);
  digit/ID tokens (`gstr3b`, `42000000`) and
  non-ASCII (`échéance`, Devanagari) are returned unchanged.
- **Search recall:** a corpus where the query word and the document word are
  morphological variants returns the document (both the FTS5 path and, forced,
  the fallback scorer).
- **Context recall:** `context "governing law"` surfaces a `governed by …` chunk
  as evidence (the `keep()` filter no longer discards it).
- **Provenance:** an exact hit is tagged exact; a stem-only hit is tagged
  `~approx`; the legend appears when an approx line is present.
- **Honesty guardrails (regression against over-stemming damage):** an ID / PAN /
  `42,000,000` / `31/12/2026` / `Échéance` value is displayed literally and not
  merged with a stemmed neighbor; a `context` answer value is byte-identical to
  the source.
- **No regression:** the existing 176 tests stay green after the schema bump +
  rebuild.

## 10. Risks & mitigations

| Risk | Mitigation |
|------|------------|
| Porter over-merges → looser evidence | Agent-layer `~approx` tagging now; reranker (#3) filters later. It's a deliberate, signaled trade. |
| Stem lands mid-word in position code | Positions/counts stay on literal `tokenize()`; stemming only via `stems()` set membership. Tested. |
| Vendored Python Porter diverges from SQLite porter | Not required to match — Python side is authoritative for reported matches; FTS is only a recall superset. |
| Existing indexes silently keep old tokenizer | Schema-version bump forces a one-time rebuild on next `sync`. Tested. |
| Exact IDs/amounts damaged | Digit/non-ASCII tokens never stemmed; values extracted from raw text. Regression-tested. |
